# 自查清单

> 改完代码后，从 diff 和验证证据两个角度过一遍。
> 目标不是证明“我写完了”，而是尽快找出还没补齐的地方。

## 1. 声明对齐

- `任务池.md` 里自己的任务行是否和实际 diff 一致
- 原始需求是否已经沉淀进任务行，没有只停留在聊天上下文里
- 任务行的 Scope 是否覆盖实际 diff，没有夹带未声明改动
- 范围如果扩大了，是否已经先更新任务行里的 `Scope` / `风险备注` 或回退多余改动
- 是否只更新了自己负责的任务行，没有误改别人的状态和风险备注
- 状态是否按 `待 -> 析 -> 做 -> 待验 -> 删除 / 归档` 或阻塞路径正确流转

## 2. 影响面

- 改公开接口、数据结构、配置时，是否列出了所有调用方和受影响业务模块
- 兼容改动还是破坏性改动，是否说清楚了
- 是否与其他 `[析]`、`[做]`、`[阻]`、`[待验]` 状态任务存在未处理的 Scope 冲突
- 高风险改动是否补了 `影响分析.md`

## 3. 子代理复核

- 是否只有 Main Agent 更新了任务池状态、`子代理`、`验证证据` 和 `风险备注`
- 子代理是否遵守交接包里的允许读取、允许修改和禁止事项
- `Worker` / `DocSync` 是否只改了指定 Scope，没有越权改文件或覆盖他人改动
- `Explorer` / `Verifier` 是否保持只读，没有修改代码或文档
- Main Agent 是否复核了子代理 diff、验证结论和文档同步结果

## 4. 验证证据

- 跑了哪些命令
- 自动化结果如何：通过 / 失败 / 跳过
- 没有自动化时，手工验证了哪些路径
- 是否已经移动到“待验收”，并写清 `验收方`、`验收方式`、`验证证据`
- 关键边界是否真的验证过：空值、越界、查不到、外部失败、并发冲突

## 5. 可读性

- 新增或修改的代码逻辑是否带中文注释
- 复杂逻辑的注释是否解释了“为什么”
- 命名是否能直接看出职责，不需要读实现才理解

## 6. 文档同步

- 模块功能、边界、流程、规则变化是否同步到对应业务模块文档
- 接口 / 依赖变化是否同步到 `架构.md`
- 新坑是否补到 `坑点.md`
- 新模式是否补到 `模式.md`
- 任务状态、待验收信息和技术决策是否同步到 `任务池.md`

## 7. 风险结论

- 当前改动最大的回归风险是什么
- 哪些点还需要人工验收
- 如果这次先不做的内容以后再做，最容易踩的坑是什么
