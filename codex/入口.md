## 会话开始先按这个顺序读

1. `ai_constraints/codex/任务池.md`：找到自己已认领的任务行，或先为新需求在“正在执行”建立一个 `[析]` 状态任务行
2. `ai_constraints/codex/模块/{业务模块}.md`：理解该业务模块的目标、边界、流程、规则和代码路径
3. `ai_constraints/codex/子代理.md`：只有任务复杂、需要并行探索 / 实现 / 验证 / 文档同步时读取

只是问问题、读代码、做分析时，不需要改任何文档。只有准备实现时，才进入 `工作流.md`。

## 硬规则

1. 先探索事实，再做决策。能从代码、配置、文档确认的事实，不要先问用户。
2. 当前窗口收到新需求时，先在 `任务池.md` 的“正在执行”创建或认领任务行，并把状态标成 `[析]`，避免其他窗口误碰。
3. 一次只推进一个明确任务。任务范围、边界、验证与验收方式以 `任务池.md` 里的任务行为准。
4. 动代码前，先确认自己的任务行至少已经写清楚：
   - 任务
   - 模块
   - Scope
   - 当前动作
   - 验证
   - 风险备注
5. 状态流转固定为：`[待] -> [析] -> [做] -> [待验] -> 删除 / 归档`；卡住时改成 `[阻]`。
6. 只改自己任务行对应的代码范围，也只更新自己负责的任务行状态和风险备注。
7. 其他窗口不得修改处于 `[析]`、`[做]`、`[阻]`、`[待验]` 状态且 `Owner` 不是自己的任务行。
8. 如果发现和其他进行中的任务 Scope 重叠，先把自己的任务标成 `[阻]`，在风险备注写明冲突点，不要硬改。
9. 新增或修改的代码逻辑必须补中文注释；复杂逻辑要解释“为什么这样做”，不要只复述代码。
10. 改完先完成验证和必要文档同步，再做自查；`Verifier` 与 `DocSync` 可以并行，但必须由 Main Agent 复核。
11. 改公开接口、模块依赖或外部集成时，必须同步 `架构.md` 和对应业务模块文档。
12. 不提交密钥、Token、凭证；提交说明统一使用中文。
13. 新增第三方依赖时，在 `任务池.md` 的“技术决策”里补一条原因。
14. Main Agent 是当前任务的唯一负责人，负责是否派发子代理、合并结果、验证结论和任务池状态流转。
15. 子代理只执行 Main Agent 明确分派的局部任务；除指定 Scope 外，不得改文件、改任务池状态或提交 Git。
16. 实现完成后默认派 `Verifier` 做验证；涉及接口、模块规则、依赖或流程变化时，并行派 `DocSync` 同步文档。
17. 任务进入“待验收”后，`验收方` 为 `用户` 时等待用户验收并删除；`验收方` 为 `AI` 时由 Main Agent 验收，通过后自行删除或归档。

## Plan Mode 约定

- 需要实现、重构或大范围调整时，优先按 Plan Mode 工作：先探索，再把决策补齐，确认没有高风险空白后再动代码。
- 提问前至少做一轮定向探索：查任务行、查对应业务模块文档、查相关代码路径、查调用方。
- 只要规范、接口、边界条件还没定清，就继续停留在 `[析]` 阶段，不要边写边想。
- 对小改动可以快速前进，但也要把默认假设写进对应任务行的“风险备注”。

## 子代理约定

- 子代理采用短生命周期模式，不设长期常驻角色团队。
- Main Agent 在 `[析]` 阶段判断是否需要子代理；需要时按 `子代理.md` 写清角色、目标、允许读取、允许修改、禁止事项和期望输出。
- `Explorer` 和 `Verifier` 默认只读；`Worker` 和 `DocSync` 只能改 Main Agent 指定的 Scope。
- 子代理完成后，Main Agent 必须复核 diff、测试和文档，再决定是否回写任务状态。

## 上下文加载策略

- 任意 Markdown 文件超过 200 行，先用 Grep 或关键字检索，不要整篇通读。
- 改某个任务时，先读对应业务模块文档，再决定是否需要补读全局 `架构.md`。
- 修问题先查 `坑点.md`，做功能先查 `模式.md`，避免重复踩坑或重复造轮子。
