## 1. 先判定模式

| 模式 | 触发条件 | 下一步 |
|------|----------|--------|
| 只读模式 | 提问、解释、读代码、分析方案、不落地 Review | 必要时读 `工作流/只读.md` |
| 微改模式 | 单文件、低风险、Scope 明确、不影响公开接口 / schema / 认证 / 支付 / 配置 / 核心流程，且无并行冲突迹象 | 读 `工作流/微改.md` |
| 轻量模式 | 1 个文件需占用 Scope，或同一影响域 2-3 个文件；风险和验证方式明确 | 读 `工作流/轻量.md` |
| 完整模式 | 4 个及以上文件、跨影响域、跨顶层目录、高风险、边界不清，或用户要求严格流程 / 独立 Review / 多子代理 | 读 `工作流/完整.md` |

命中任一完整模式条件时，按完整模式处理；执行中发现风险升级时，先切换模式并补齐对应上下文。

## 2. 上下文加载路由

1. 先读用户请求里明确给出的文件、路径、符号、报错或 diff。
2. 需要修改、判断并行冲突或锁定 Scope 时，读 `ai_constraints/codex/任务池.md`。
3. 需要判断影响域时，先读目标文件和引用处；只有影响业务 / 技术模块、启动入口或依赖关系时，才读模块文档或 `ai_constraints/codex/架构.md`。
4. 需要规则判断时，再按触发条件读取专项文档；不要为了流程完整预读全套文档。
5. 任意 Markdown 文件超过 200 行时，先用 `rg` / 关键词定位，不整篇通读。

## 4. 不可跳过的边界

- 先探索事实，再做决策；能从仓库确认的事实不要先问用户。
- 只读模式不改文件、不改任务池、不派子代理。
- 准备修改前必须明确 Scope；发现 Scope 冲突时停止并按 `任务池.md` 规则处理。
- 不修改其他 Owner 的执行中任务；子代理不得改任务池状态。
- 不提交密钥、Token、凭证；提交说明统一使用中文。
- 新增或修改代码逻辑必须有中文注释，复杂逻辑要说明“为什么”。
- 实现完成必须验证；无法自动验证时，在最终回复和任务记录里说明手工验证或残余风险。
