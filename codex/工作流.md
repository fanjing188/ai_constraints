# Codex 工作流

> 只有准备实现时才走这份工作流。
> 目标是把“探索、决策、实施、验证”拆开，避免 Codex 边猜边写。

## 1. 探索事实

- 先判断本次是修问题、加能力，还是只做结构调整。
- 必读：
  - `ai_constraints/codex/任务池.md`
  - `ai_constraints/codex/当前任务.md`
- 按需补读：
  - `ai_constraints/codex/架构.md`
  - `ai_constraints/codex/模块/{name}.md`
  - `ai_constraints/codex/规范.md`
  - `ai_constraints/codex/模式.md`
  - `ai_constraints/codex/坑点.md`
- 先看代码再问问题。只要答案能从仓库里找到，就不要把问题抛给用户。

## 2. 补齐决策

- 把下面几件事先说清楚，再进入实现：
  - 成功标准：这次改完，什么行为必须成立
  - 范围边界：明确不改什么、不处理什么
  - 接口变化：哪些输入、输出、错误路径会变
  - 风险点：是否影响调用方、配置、存储、兼容性
  - 验证方法：准备用哪些测试或手工路径证明改动成立
- 满足任一条件时，先补 `ai_constraints/codex/影响分析.md`：
  - 改两个及以上模块
  - 改公开接口
  - 改数据库或存储结构
  - 删除、重命名已有能力
  - 新增第三方依赖

## 3. 写入 当前任务.md

把 `ai_constraints/codex/当前任务.md` 覆盖成当前执行契约：

```md
做的是：[任务池里的哪个任务]
改什么：[一句话]
不加什么：[本次明确不做]
验证方式：[测试命令 / 手工路径]
停在哪：[准备动代码]
```

规则：
- 任务池里没有这项任务，先补进去，再开工
- 如果范围扩大，先更新 `当前任务.md`，不要悄悄扩 diff
- 小任务也要写，只是可以写得更短

## 4. 执行、验证、同步

按下面顺序推进，顺序不能颠倒：

1. 做最小实现：先改必要路径，不顺手修别的问题
2. 跑验证：
   - `bash ai_constraints/scripts/verify.sh [file ...]`
   - 需要时补跑更大范围测试
3. 同步文档：
   - 接口 / 依赖变化：更新 `架构.md` 和 `模块/{name}.md`
   - 新坑：更新 `坑点.md`
   - 新模式：更新 `模式.md`
   - 任务完成：更新 `任务池.md`
4. 对照 `自查清单.md` 做 diff 自查
5. 把 `当前任务.md` 的“停在哪”更新成实际状态，例如：
   - 已完成并已验证
   - 已完成，待人工验收
   - 卡在某个阻塞点
