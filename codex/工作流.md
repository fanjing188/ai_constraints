# Codex 工作流

> 多个 Codex 窗口并行执行不同任务时，都走这份工作流。
> 单个任务内部采用 Main Agent 主控模式：主控代理负责决策、派发子代理、复核结果和回写状态，子代理只执行明确分派的局部工作。

## 1. 接收需求并占位认领

- 如果当前窗口收到的是新需求，先在 `ai_constraints/codex/任务池.md` 的“正在执行”新增任务行。
- 新建任务行时，最少先写：
  - `状态`：`[析]`
  - `任务`
  - `Owner`
- 如果任务已经存在且状态是 `[待]`，先把 `Owner` 写成自己，再把状态改成 `[析]`。
- 如果任务已经存在且 `Owner` 已经是自己，直接继续推进。
- 如果任务已经存在但 `Owner` 不是自己，不要硬改。
- 处于 `[析]`、`[做]`、`[阻]`、`[待验]` 状态的任务行，默认视为已被对应窗口锁定，其他窗口和子代理都不改。

## 2. 分析需求并补全任务行

- 分析阶段至少补全这几个字段：
  - `任务`
  - `模块`
  - `Owner`
  - `Scope`
  - `验证`
  - `当前动作`
  - `风险备注`
- 任务池里没有这项任务，先补任务行，再开工。
- 如果分析后发现和其他 `[析]`、`[做]`、`[阻]`、`[待验]` 状态任务的 `Scope` 明显重叠，不要硬改；先把自己的任务标成 `[阻]`，并在“风险备注”里写明原因。
- Main Agent 在本阶段判断是否需要子代理：
  - 简单只读问题：不派子代理。
  - 小型单文件实现：可以由 Main Agent 直接做。
  - 多文件、跨模块或高不确定性任务：先派 `Explorer` 做只读影响分析。
  - 可拆分实现：派一个或多个 `Worker`，每个 `Worker` 必须有互不重叠的写入 Scope。
- 如果决定派发子代理，在任务行的 `子代理` 字段记录角色、目标和 Scope 摘要。
- 分析完成后，再把状态从 `[析]` 改成 `[做]`。

## 3. 加载模块上下文

- 必读：
  - `ai_constraints/codex/模块/{模块名}.md`
- 按需补读：
  - `ai_constraints/codex/子代理.md`
  - `ai_constraints/codex/架构.md`
  - `ai_constraints/codex/规范.md`
  - `ai_constraints/codex/模式.md`
  - `ai_constraints/codex/坑点.md`
- 先读模块文档里的“代码路径”，再去加载相关实现、调用方和测试。
- 先看代码再问问题。只要答案能从仓库里找到，就不要把问题抛给用户。
- 派发子代理前，Main Agent 必须用 `子代理.md` 的交接包写清允许读取、允许修改和禁止事项。

## 4. 执行实现

- 只在任务行声明的 `Scope` 范围内修改代码。
- 一次只解决当前任务，不顺手修别的问题。
- `Worker` 子代理只能改 Main Agent 指定的 Scope；发现范围不够时返回风险，不得自行扩大。
- 满足任一条件时，先补 `ai_constraints/codex/影响分析.md`：
  - 改两个及以上业务模块
  - 改公开接口
  - 改数据库或存储结构
  - 删除、重命名已有能力
  - 新增第三方依赖
- 如果实现过程中发现范围扩大，先更新任务行里的 `Scope`、`当前动作` 或“风险备注”，不要悄悄扩 diff。
- Main Agent 必须复核子代理修改，确认没有越权、覆盖他人改动或偏离任务目标。

## 5. 验证与文档同步

实现完成后按下面规则推进：

1. 默认派 `Verifier`：
   - 执行 `bash ai_constraints/scripts/verify.sh [file ...]`
   - 按任务行的 `验证` 补跑必要测试或手工验证
   - 检查 diff 是否符合 Scope，且没有夹带未声明改动
2. 满足任一条件时，并行派 `DocSync`：
   - 模块功能、边界、规则或关键流程变化
   - 接口、依赖、配置或外部集成变化
   - 新踩坑需要写入 `坑点.md`
   - 新可复用模式需要写入 `模式.md`
3. Main Agent 汇总 `Verifier` 和 `DocSync` 输出：
   - 测试失败：回到 `[做]` 修复，或标成 `[阻]` 并写明阻塞。
   - 文档不同步：先补齐文档，再移动到“待验收”。
   - 子代理越权：先停止合并，收敛或回退越权部分，再继续。

## 6. 自查并移动到待验收

- 对照 `ai_constraints/codex/自查清单.md` 做 diff 自查。
- 在任务行的 `子代理` 和 `风险备注` 记录子代理结论摘要；没有派发则写 `未使用` 或省略。
- 已完成开发、验证和必要文档同步后，把任务从“正在执行”移动到“待验收”，状态改成 `[待验]`。
- 移动到“待验收”时必须写清：
  - `验收方`：`用户` 或 `AI`
  - `验收方式`
  - `验证证据`
  - `风险备注`
- 有阻塞时，不移动板块；状态改成 `[阻]`，并在“风险备注”写明原因。

## 7. 验收并关单

- 按“待验收”里的 `验收方式` 执行最终确认。
- `验收方` 为 `用户` 时，等待用户验收；通过后由用户删除任务行，或授权 AI 删除 / 归档。
- `验收方` 为 `AI` 时，Main Agent 执行验收；通过后从任务池删除任务行，需要留痕时写入“里程碑归档”或 `归档/{milestone}.md`。
- 验收不通过时：
  - 需要继续修改：移回“正在执行”，状态改成 `[做]`
  - 需要等待外部条件：移回“阻塞 / 需人工介入”，状态改成 `[阻]`
- 删除或归档前，在最终回复里说明验收结论、残余风险或后续动作。
