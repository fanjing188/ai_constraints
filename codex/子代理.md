# 子代理协作协议

> 本文定义 Main Agent 如何派发短生命周期子代理。
> 子代理只执行被明确分派的局部任务，不拥有完整任务，也不负责最终状态流转。

## 基本模型

- Main Agent 是当前任务的唯一负责人，负责需求分析、任务拆分、派发决策、子代理结果复核、合并决策、验证结论和任务池回写。
- 子代理是 Main Agent 的临时执行单元，只能在交接包声明的目标、权限和 Scope 内工作。
- 轻量模式默认不派子代理；命中完整模式派发评估条件时，Main Agent 必须记录决策，平台允许且任务有并行收益时才创建真实 Sub-agent。
- 如果平台提供 `spawn_agent`、`worker`、`explorer` 或等价工具，且当前任务满足派发条件，Main Agent 应创建真实子代理并记录标识；角色有限时，`Verifier` 和 `DocSync` 可用通用子代理承载，但交接包要写清实际职责。
- 子代理之间不直接协商任务边界；如果发现冲突、越权或信息不足，返回风险，由 Main Agent 决策。
- `任务池.md` 的状态、Owner、Scope、验收和风险只允许 Main Agent 修改。
- 多窗口并行规则仍然有效：子代理不能绕过任务池锁，也不能修改其他窗口负责的任务行。

## 子代理角色

| 角色 | 适用场景 | 写权限 | 输出重点 |
|------|---------|--------|----------|
| `Explorer` | 复杂需求、跨模块影响、未知代码路径 | 不允许写文件 | 事实、路径、调用方、风险、建议切片 |
| `Worker` | 明确 Scope 内的实现切片 | 只允许改指定 Scope | 已改内容、修改文件、验证建议、残余风险 |
| `Verifier` | 实现完成后的测试和 diff 风险检查 | 不允许改代码和文档 | 测试命令、结果、失败原因、回归风险 |
| `DocSync` | 接口、模块规则、依赖或流程变化后的文档同步 | 只允许改指定文档 | 已同步文档、未覆盖事项、需要主控确认点 |

## 模式与派发边界

- 只读和微改模式不派子代理；只读只回答，微改由 Main Agent 直接处理。
- 轻量模式默认不派子代理；如果用户明确要求独立 Review，或改动范围升级为完整模式，再按完整模式重新评估。
- 完整模式必须做派发决策：多问题域优先多派 `Explorer`，多写入 Scope 优先多派 `Worker`，实现后按风险派 `Verifier` / `DocSync`。
- Main Agent 派出 `Explorer` 后，不重复排查同一问题域；如果没有其他不重叠工作，先等待结果再继续。
- Main Agent 派出 `Worker` 后，不在同一写入 Scope 内并行改同一批文件；如需统一调整，先等子代理返回并复核。

## 派发规则

- 微改模式单文件低风险不派子代理；轻量模式影响 1 个文件需任务池锁 Scope，或影响 2-3 个文件但都在同一模块内，完成后必须验证，通常不派子代理。
- 命中任一完整模式派发评估条件时，必须记录是否派 `Explorer` 的决策：
  - 影响 4 个及以上文件
  - 影响 2 个及以上业务模块
  - Scope 覆盖 2 个及以上顶层目录
  - 改公开接口、schema、认证、支付、配置、外部集成、核心流程或模块边界
  - 代码路径、调用方或风险边界不明确
- 用户明确要求严格流程、独立 Review 或多子代理并行时，即使文件数量较少，也按完整模式记录派发决策。
- 平台允许且风险边界不清时，优先先派 `Explorer`；平台不允许、上级系统禁止、范围已由代码和文档确认或没有并行收益时，在任务行写 `未使用：原因`。
- 能拆出互不重叠写入 Scope，且平台允许并有并行收益时，并发派多个 `Worker`。
- 实现完成后必须完成验证；高风险、多文件、跨模块、改公开接口或用户要求独立复核时，平台允许则派 `Verifier` 执行测试、检查 diff 与任务 Scope 是否一致。
- 满足任一条件时，必须记录是否派 `DocSync` 的决策；平台允许且文档 Scope 可隔离时，优先与 `Verifier` 并行派 `DocSync`：
  - 改公开接口
  - 改数据库 schema、模型或迁移
  - 改业务模块边界、核心规则或关键流程
  - 改模块依赖、配置或外部集成
  - 新增可复用模式或踩坑记录
- 命中派发评估条件但未派发时，必须在任务行风险里写 `未使用：原因`，原因包括单文件小改无并行收益、平台未暴露子代理能力、上级系统明确禁止、Scope 无法隔离或子代理创建失败，不得只写 `未使用`。

## 并发拆分策略

- `Explorer` 按问题域拆：业务影响、代码路径、验证风险。
- `Worker` 按写入 Scope 拆：前端页面/组件、API/service、数据模型/schema、文案/i18n、文档。
- 多个 `Worker` 的 `允许修改` 不得重叠；如果无法拆出互不重叠 Scope，不派 `Worker`，由 Main Agent 统一实现并记录原因。
- 并发派发时，Main Agent 先连续创建多个子代理，再等待结果；不要创建一个、等待一个、再创建下一个。
- 没有不重叠的探索、实现或验证工作时，Main Agent 等待已派发子代理返回，不制造重复工作。
- `Verifier` 与 `DocSync` 同时满足派发条件时，在实现完成后并行启动；Main Agent 等已派发的子代理都返回后再移动到“待验收”。

## 可观察记录

- 日志里能看到真实派发，通常表现为子代理创建工具调用、返回的 Agent ID、昵称或子会话标识。
- `任务池.md` 的当前动作或风险必须记录派发决策；真实派发时记录 `角色(Agent ID 或昵称)：目标 / Scope / 状态或结论`，未派发时记录 `未使用：原因`。
- 只出现 `Explored`、`已分析`、`计划派发`、`应派发` 这类文字，不算已经真实派发子代理。
- 如果子代理创建失败，Main Agent 必须记录失败原因和降级处理方式，再决定是否继续由主控实现。

## 派发交接包

Main Agent 派发子代理时，必须写清下面字段：

```md
- 任务ID：
- 子代理角色：
- Agent标识：
- 目标：
- 允许读取：
- 允许修改：
- 禁止事项：
- 必须遵守：
- 期望输出：
```

字段要求：

- `任务ID` 必须对应 `任务池.md` 中当前 Main Agent 负责的任务行。
- `Agent标识` 在创建前写 `待创建`，创建成功后补 Agent ID、昵称或会话标识。
- `允许读取` 写目录、文件或关键词范围；探索型任务也要说明重点。
- `允许修改` 对只读角色写 `无`；对可写角色必须列出明确文件或目录。
- `禁止事项` 至少包含不得修改其他任务行、不得扩大 Scope、不得提交 Git。
- `期望输出` 必须要求子代理说明验证结果、风险和需要 Main Agent 继续处理的事项。

## 子代理返回格式

子代理完成后按固定格式返回：

```md
- 已完成：
- 修改文件：
- 验证命令与结果：
- 风险：
- 需要 Main Agent 继续处理：
```

返回要求：

- 只读角色的 `修改文件` 必须写 `无`。
- 运行测试失败时，必须写清失败命令、失败现象和初步定位。
- 发现 Scope 冲突、权限不足或不确定决策时，不要自行扩大范围，直接返回给 Main Agent。
- `Worker` 和 `DocSync` 不得把自己的输出等同于最终完成；最终结论由 Main Agent 复核后给出。

## Main Agent 汇总要求

- 先检查子代理是否越权修改文件，再看实现和测试结论。
- 对 `Worker` 输出必须复核 diff，确认没有顺手改、范围漂移或覆盖他人改动。
- 对 `Verifier` 输出必须判断测试是否足够覆盖任务行里的验证要求。
- 对 `DocSync` 输出必须确认文档变化和代码事实一致。
- 汇总后再更新 `任务池.md` 的当前动作、风险和状态；子代理结论写在当前动作或风险里。
