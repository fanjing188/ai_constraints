# Codex 编码范式

> 这份规范描述的是 Codex 写代码时必须遵守的工作方式，不只是语言风格。
> 如果项目已有更细的语言级规范，把它们继续写在这里。

## 工作方式

- 先读后改：先看任务池表格、对应业务模块文档、相关实现和调用方，再决定怎么改
- 一次只做一个任务：每个窗口一次只推进自己负责的一项任务
- 需求先占位：当前窗口收到新需求时，先在任务池“正在执行”创建任务行并认领，再分析和实现
- 最小 diff：一次只解决当前任务，不顺手修、不提前抽象、不偷偷扩范围
- 范围受任务行约束：只改自己任务行声明的 `Scope`，也只更新自己负责的任务行状态和风险备注
- 运行中的任务要锁住：`[析]`、`[做]`、`[阻]`、`[待验]` 状态的任务行默认只允许 `Owner` 修改
- 主控代理负责制：Main Agent 决定是否派发子代理，并负责复核、合并和任务池状态流转
- 子代理范围受交接包约束：只读角色不改文件，可写角色只改指定 Scope
- 先定接口再写实现：公开能力先把输入、输出、错误路径写清楚
- 先改主路径，再补边界：避免一开始就被防御性分支淹没
- 所有假设可追溯：不确定但需要继续推进时，把默认假设写进任务行的“风险备注”

## 命名与结构

- **文件名**：[例：kebab-case，如 `user-service.ts`]
- **变量 / 函数**：[例：camelCase]
- **类 / 组件 / 类型**：[例：PascalCase]
- **常量**：[例：UPPER_SNAKE_CASE]
- **数据库字段**：[例：snake_case]
- 目录按职责拆开，不要让控制层、业务层、存储层混在一个文件里

## 注释要求

- 新增或修改的代码逻辑必须补中文注释
- 复杂逻辑注释解释“为什么这样做”，不要只复述代码
- 公开函数、公共类型、外部接口要有注释说明输入、输出和约束
- TODO 必须说明触发条件和下一步，例如：`// TODO(认证重构): 合并重复校验逻辑`

## 接口与错误处理

- 不直接抛字符串；统一抛明确的错误类型或返回明确的错误结构
- 所有边界路径都要有明确行为：空值、越界、查不到、外部服务失败、并发冲突
- 破坏性接口变更必须同步调用方，不能只改被调用处
- 外部依赖失败时，优先写清楚是重试、降级还是直接报错

## 验证要求

- 新能力、公开接口变更、关键修复都必须有验证证据
- 自动化优先；没有自动化时，要把手工验证路径写进任务行的“验证”或“风险备注”
- 验证和验收分开记录：`验证` 解决技术正确性，`验收` 解决需求是否真正成立
- 改到核心模块时，不只跑单测，要补跑更高一层的验证
- 每次实现完成后，都要执行 `bash ai_constraints/scripts/verify.sh [file ...]`
- 使用子代理时，Verifier 输出必须由 Main Agent 复核后才能作为验证结论

## 文档与提交

- 对外接口、模块依赖、外部集成变化，必须同步 `架构.md` 和对应业务模块文档
- 新踩坑记录到 `坑点.md`，新可复用写法记录到 `模式.md`
- 任务状态变化、风险、验证结果和待验收信息同步 `任务池.md`
- 验收通过后从任务池删除；需要留痕时写入“里程碑归档”或 `归档/{milestone}.md`
- 子代理派发和结果只在 `子代理` 字段写摘要，详细交接和权限以 `子代理.md` 为准
- Git 提交说明统一用中文，推荐格式：`模块：动作 + 目的`
